1. PROPÓSITO GENERAL
================================================================================

Este proyecto implementa un sistema multi-agente automatizado que analiza el
cumplimiento de la Medida 83 (CTOGÉSIMA TERCERA) del IFT (Instituto Federal
de Telecomunicaciones de México).

La Medida 83 establece que:

  "El Agente Económico Preponderante no podrá contactar al Usuario Final que
   haya sido portado desde su red durante los 60 días naturales posteriores
   a la ejecución de la portabilidad."

El sistema:
  - Consulta una base de datos PostgreSQL con registros de portabilidad móvil
  - Analiza cuantitativamente el cumplimiento de la ventana de 60 días
  - Contextualiza los hallazgos dentro del marco regulatorio vigente
  - Produce un informe narrativo formal en estilo técnico-regulatorio
  - Evalúa automáticamente la calidad del informe generado
  - Genera un documento Word (.docx) con texto coloreado por agente fuente


2. ARQUITECTURA GENERAL
================================================================================

El sistema sigue una arquitectura de pipeline secuencial orquestado con tres
agentes especializados, un sistema RAG (Retrieval-Augmented Generation) por
agente, y un evaluador automático (LLM-as-a-Judge).

Flujo de ejecución:

  Pregunta de análisis
         │
         ▼
  ┌─────────────────┐
  │   Orquestador   │  (sin LLM propio, coordina el flujo)
  └────────┬────────┘
           │
           ├──── Etapa 1/3 ────▶ AgenteDatos     (AZUL,   temp=0.0)
           │                        │
           ├──── Etapa 2/3 ────▶ AgenteRegulat.  (VERDE,  temp=0.1)
           │                        │
           └──── Etapa 3/3 ────▶ AgenteRedactor  (ROJO,   temp=0.3)
                                    │
                                    ▼
                              ┌──────────┐
                              │ LLMJudge │  (MORADO, temp=0.0)
                              └────┬─────┘
                                   │
                                   ▼
                           Documento Word (.docx)

Cada agente recibe como contexto los outputs de TODOS los agentes anteriores.
Si un agente falla, el pipeline continúa gracias al wrapper _safe_run().

4.2 agents/base_agent.py — Capa Base de Agentes
--------------------------------------------------------------------------------

Archivo: agents/base_agent.py (109 líneas)
Rol: Define la interfaz y comportamiento común de todos los agentes.

Clases:

  AgentResult (dataclass):
    - agent_name: str         → Nombre del agente que produjo este resultado
    - content: str            → Texto principal de la respuesta
    - metadata: dict          → Info adicional (fuentes, queries, parámetros)
    - error: Optional[str]    → Mensaje de error si falló; None si exitoso
    - succeeded: bool         → Propiedad derivada: True si error is None
    - __str__                 → "AgentResult(nombre, OK/ERROR, N chars)"

  BaseAgent (ABC):
    - __init__(temperature):
        Instancia ChatOllama configurado con el modelo y URL de config.py.
        Crea un logger con el nombre de la subclase.

    - run(**kwargs) → AgentResult [abstracto]:
        Cada subclase implementa su lógica aquí. Puede lanzar excepciones.

    - _safe_run(**kwargs) → AgentResult:
        Wrapper que envuelve run() con try/except. Si run() lanza excepción:
        → Loguea el error con stacktrace completo (exc_info=True)
        → Retorna AgentResult con error=str(e) y content con mensaje de error
        → NUNCA propaga la excepción → el pipeline continúa siempre

Patrón de diseño: Template Method + Strategy. El Orquestador siempre llama
_safe_run(), nunca run() directamente, garantizando resiliencia.


4.3 agents/agente_datos.py — Agente de Datos (AZUL)
--------------------------------------------------------------------------------

Archivo: agents/agente_datos.py (141 líneas)
Rol: Análisis cuantitativo contra la base de datos PostgreSQL de portabilidad.
Color en Word: AZUL (0, 70, 127)
Temperatura: 0.0 (generación determinista de SQL)

Mecanismo:
  1. Consulta el RAG de schema (rag_datos.py → colección "schema_docs")
     para obtener contexto de negocio sobre las tablas y columnas.
  2. Construye una pregunta enriquecida con SYSTEM_PROMPT_TEMPLATE que
     incluye el contexto de esquema + la pregunta original.
  3. Crea un SQL Agent de LangChain con patrón ReAct:
     - Agent type: "zero-shot-react-description" (más robusto con modelos
       locales que "openai-tools", ya que no depende de tool-calling
       estructurado del modelo)
     - max_iterations=15: permite múltiples intentos de corrección de SQL
     - max_execution_time=180: timeout de 3 minutos por ejecución
     - handle_parsing_errors=True: resiliente a errores de parsing del LLM
     - early_stopping_method="generate": si se agotan las iteraciones,
       genera una respuesta parcial en vez de fallar
  4. El SQL Agent formula queries SQL, las ejecuta contra PostgreSQL,
     interpreta resultados, y los formatea.

Métricas objetivo del análisis:
  - Total de portaciones ejecutadas en el periodo
  - Número y porcentaje de casos de contacto prohibido (dentro de 60 días)
  - Desglose por concesionario/operador de los casos de incumplimiento
  - Evolución temporal (mensual) del nivel de incumplimiento

Metadatos producidos:
  - schema_docs_retrieved: cantidad de fragmentos de esquema recuperados
  - question: la pregunta original
  - schema_sources: lista de archivos fuente usados del RAG

Dependencias exclusivas:
  - langchain_community.agent_toolkits.create_sql_agent
  - langchain_community.agent_toolkits.sql.toolkit.SQLDatabaseToolkit
  - db.postgres_client.get_sql_database (conexión SQLAlchemy)

Fallback: Si no hay documentos en schema_docs/, el agente opera
solo con el DDL crudo que el SQL Agent descubre de la BD.


4.4 agents/agente_regulatorio.py — Agente Regulatorio (VERDE)
--------------------------------------------------------------------------------

Archivo: agents/agente_regulatorio.py (120 líneas)
Rol: Proporcionar el marco legal y normativo de la Medida 83.
Color en Word: VERDE (0, 112, 0)
Temperatura: 0.1 (preciso con mínima variación)

Inputs:
  - question: pregunta original de análisis
  - datos_result: texto con hallazgos cuantitativos del Agente Datos

Mecanismo:
  1. Consulta el RAG regulatorio (rag_regulatorio.py → colección "regulatorio")
     que indexa PDFs de data/docs/regulatorio/.
  2. Los documentos recuperados incluyen metadatos de fuente y número de página.
  3. Cadena LCEL simple: ChatPromptTemplate | ChatOllama | StrOutputParser
  4. El prompt incluye tanto el contexto regulatorio como los hallazgos del
     Agente Datos para contextualizar legalmente los números.

Secciones que produce:
  1. TEXTO NORMATIVO: Cita exacta de la Medida 83
  2. ALCANCE Y PROPÓSITO: A quién aplica, qué es "contacto"
  3. SANCIONES: Consecuencias del incumplimiento
  4. CONTEXTUALIZACIÓN: Interpretación legal de los hallazgos cuantitativos
  5. FUENTES: Resoluciones, acuerdos y artículos específicos

Metadatos producidos:
  - sources_cited: lista de fuentes únicas (set de archivos PDF)
  - regulatory_docs_retrieved: cantidad de fragmentos recuperados
  - question: la pregunta original

Fallback: Si no hay PDFs disponibles en data/docs/regulatorio/, el agente
usa su conocimiento interno (del entrenamiento de llama3.1) sobre la
normativa del IFT y la Medida 83.


4.5 agents/agente_redactor.py — Agente Redactor (ROJO)
--------------------------------------------------------------------------------

Archivo: agents/agente_redactor.py (119 líneas)
Rol: Sintetizar los outputs de los dos agentes anteriores en un informe
     narrativo formal apropiado para un informe regulatorio oficial.
Color en Word: ROJO (192, 0, 0)
Temperatura: 0.3 (la más alta del sistema, para prosa fluida y no repetitiva)

Inputs:
  - question: pregunta original de análisis
  - datos_result: texto con hallazgos cuantitativos del Agente Datos
  - regulatorio_result: texto con análisis regulatorio del Agente Regulatorio

Mecanismo:
  1. Consulta el RAG de plantillas (rag_redactor.py → colección "plantillas")
     que indexa archivos .txt de data/docs/plantillas/.
  2. Recibe datos_result + regulatorio_result como bloques de contexto en el prompt.
  3. Cadena LCEL simple: ChatPromptTemplate | ChatOllama | StrOutputParser
  4. El prompt define una estructura rígida de 5 secciones para el informe.

Estructura del informe generado:
  I.   ANTECEDENTES Y BASE LEGAL
       Descripción de la Medida 83, propósito, citas normativas.
  II.  METODOLOGÍA DE ANÁLISIS
       Cómo se analizaron los datos de portabilidad, fuentes de datos.
  III. HALLAZGOS PRINCIPALES
       Cifras totales, porcentajes, desglose por operador, tendencias.
  IV.  MARCO REGULATORIO Y CONSECUENCIAS
       Integración del análisis legal con los hallazgos cuantitativos.
  V.   CONCLUSIONES Y RECOMENDACIONES
       Síntesis ejecutiva y recomendaciones concretas.

Instrucciones de estilo definidas en el prompt:
  - Español formal, estilo técnico-regulatorio (como documentos del IFT)
  - Referencias cruzadas: "De conformidad con la Medida 83..."
  - Integración fluida de cifras con citas normativas
  - Texto autocontenido (comprensible sin contexto adicional)
  - Longitud objetivo: 500-700 palabras
  - No repite literalmente textos de otros agentes; sintetiza e integra

Metadatos producidos:
  - template_docs_used: cantidad de plantillas recuperadas
  - temperature: 0.3
  - question: la pregunta original

Fallback: Si no hay plantillas disponibles, el agente usa estilo regulatorio
estándar del IFT: lenguaje técnico-jurídico, párrafos densos, citas en
formato "De conformidad con [artículo]..."


4.6 agents/orquestador.py — Orquestador del Pipeline
--------------------------------------------------------------------------------

Archivo: agents/orquestador.py (162 líneas)
Rol: Coordinar la ejecución secuencial de los tres agentes.
NO tiene LLM propio ni RAG propio.

Clases:

  RunContext (dataclass):
    Estado completo de una ejecución del pipeline. Actúa como "registro
    histórico" de la ejecución.

    Atributos:
      - question: str                     → Pregunta de análisis original
      - run_timestamp: datetime           → Marca temporal del inicio
      - datos_result: Optional[AgentResult]      → Output Agente Datos
      - regulatorio_result: Optional[AgentResult] → Output Agente Regulatorio
      - redactor_result: Optional[AgentResult]    → Output Agente Redactor
      - judge_result: Optional[dict]       → Resultado resumido del LLM Judge
      - output_path: Optional[Path]        → Ruta al .docx generado

    Propiedades:
      - all_agents_succeeded: bool → True si los tres agentes completaron sin error
      - agents_with_errors: list[str] → Nombres de agentes que fallaron
      - summary(): str → Resumen legible del estado de la ejecución

  Orquestador:
    - __init__: Instancia los tres agentes una sola vez (reutiliza conexiones)
    - run(question) → RunContext:
        Ejecuta secuencialmente:
          1. AgenteDatos._safe_run(question=question)
          2. AgenteRegulatorio._safe_run(question=question, datos_result=...)
          3. AgenteRedactor._safe_run(question=question, datos_result=...,
                                       regulatorio_result=...)
        Cada agente recibe los outputs acumulados de los anteriores.
        Si un agente falla, su error queda en el RunContext y el pipeline
        continúa con el siguiente agente.
    - _log_stage_result: Loguea el resultado (OK con chars y metadata,
        o ERROR con mensaje y contenido parcial)

Patrón: El Orquestador NO llama al juez ni genera el Word.
Eso lo hace main.py para mantener separación de responsabilidades.


4.7 rag/rag_builder.py — Fábrica Compartida de Vectorstores
--------------------------------------------------------------------------------

Archivo: rag/rag_builder.py (226 líneas)
Rol: Centralizar la creación, ingestión y consulta de colecciones ChromaDB.

Funciones públicas:

  get_embeddings() → OllamaEmbeddings:
    Retorna modelo de embeddings "nomic-embed-text" vía Ollama local.
    No requiere API key.
    Prerequisito: ollama pull nomic-embed-text

  build_or_load_vectorstore(
      collection_name, persist_directory, docs_directory,
      file_extension=".txt", force_reingest=False
  ) → Chroma:

    Comportamiento idempotente:
      - Si la colección ya tiene documentos y force_reingest=False:
        → Carga sin re-procesar (rápido)
      - Si la colección ya tiene documentos y force_reingest=True:
        → Elimina la colección y re-ingesta desde cero
      - Si la colección no existe o está vacía:
        → Carga documentos → divide en chunks → ingesta y persiste

    Parámetros de splitting:
      - Chunk size: 1000 caracteres (configurable desde .env)
      - Chunk overlap: 200 caracteres (configurable desde .env)
      - Separadores: ["\n\n", "\n", ".", " ", ""]
      - Splitter: RecursiveCharacterTextSplitter

    Ingestión en lotes:
      - Batch size: 100 chunks por lote
      - Logging de progreso por lote

    Cross-platform:
      - str() en paths para ChromaDB (no acepta Path objects en todas las versiones)
      - use_multithreading=False para estabilidad en Windows

  get_retriever(vectorstore, k=4, search_type="similarity") → VectorStoreRetriever:
    Envuelve un vectorstore en un retriever LangChain.
    Soporta search_type: "similarity" (coseno) o "mmr" (maximal marginal relevance).

  _load_documents(docs_directory, file_extension) → list:
    Función interna de carga de documentos:
      - .pdf → PyPDFLoader (extrae texto página por página con metadatos de página)
      - Otros → TextLoader con encoding UTF-8
      - use_multithreading=False (estabilidad Windows)
      - silent_errors=True (no crashea por un archivo corrupto)
      - Fallback: si DirectoryLoader falla, intenta cargar archivo por archivo

4.11 judge/llm_judge.py — Evaluador LLM-as-a-Judge
--------------------------------------------------------------------------------

Archivo: judge/llm_judge.py (270 líneas)
Rol: Evaluador automático de calidad del informe generado.
Color en Word: MORADO (128, 0, 128)
Temperatura: 0.0 (scoring determinista y reproducible)

Clases:

  JudgeResult (dataclass):
    - scores: dict           → Puntajes 1-10 por dimensión
    - score_total: float     → Promedio de los 5 puntajes (0.0 a 10.0)
    - aprobado: bool         → True si score_total >= JUDGE_MIN_SCORE (7)
    - fortalezas: list       → Puntos fuertes del informe
    - sugerencias: list      → Sugerencias de mejora
    - resumen: str           → 2-3 oraciones de evaluación general
    - raw_response: str      → Respuesta cruda del LLM (para debugging)
    - parse_error: bool      → True si hubo error al parsear JSON

    Método:
      to_display_text() → str: Texto formateado con puntajes por dimensión,
        fortalezas y sugerencias, listo para Word o consola.

  LLMJudge:
    - __init__: Instancia ChatOllama con temperature=0.0

    - evaluate(ctx: RunContext) → JudgeResult:
        Recibe el RunContext completo del pipeline.
        Extrae el content de cada agente (o mensaje placeholder si no ejecutó).
        Construye prompt con los tres outputs + pregunta original.
        Cadena LCEL: ChatPromptTemplate | ChatOllama | StrOutputParser
        Nunca lanza excepción; errores del LLM → JudgeResult con parse_error.

    - _parse_response(raw: str) → JudgeResult:
        Parsing robusto de la respuesta del LLM:
          1. re.search(r'\{.*\}', raw, re.DOTALL) → extrae JSON aunque el
             LLM haya agregado texto antes o después
          2. json.loads() del bloque encontrado
          3. Recalcula score_total como promedio si el LLM calculó mal
          4. Redondea a 2 decimales
          5. Valida aprobado contra JUDGE_MIN_SCORE
          Si falla cualquier paso → _fallback_result()

    - _fallback_result(raw, reason) → JudgeResult:
        Resultado de fallback seguro: score_total=0.0, aprobado=False,
        sugiere revisión manual. NUNCA crashea.

Cinco dimensiones evaluadas (cada una 1-10):
  1. COMPLETITUD: ¿Se respondió la pregunta original completa?
  2. PRECISION_DATOS: ¿Cifras coherentes internamente y sin contradicciones?
  3. PRECISION_REGULATORIA: ¿Referencias a Medida 83 correctas y suficientes?
  4. COHERENCIA: ¿Los tres agentes producen narrativa integrada sin contradicciones?
  5. CALIDAD_REDACCION: ¿Texto claro, formal y apropiado para informe regulatorio?

Score total: promedio de las 5 dimensiones.
Aprobado: score_total >= 7/10 (configurable vía JUDGE_MIN_SCORE en .env).

Modos de ejecución:

  1. python main.py
     → Pipeline completo con evaluación automática.
     Usa DEFAULT_QUESTION que analiza cumplimiento de Medida 83:
       - Total de portaciones ejecutadas
       - Casos de contacto prohibido en ventana de 60 días
       - Desglose por concesionario/operador
       - Evolución mensual del incumplimiento

  2. python main.py --discover-schema
     → cmd_discover_schema():
       - Verifica conexión a PostgreSQL
       - Lista todas las tablas con get_table_names()
       - Muestra DDL completo con get_schema_info()
       - Sugiere crear archivos en data/docs/schema_docs/ con el DDL
       y descripciones de negocio para el RAG

  3. python main.py --reingest
     → cmd_reingest():
       - Re-ingesta los 3 vectorstores RAG en orden:
         1/3 Schema docs (get_schema_retriever con force_reingest=True)
         2/3 Documentos regulatorios (get_regulatorio_retriever)
         3/3 Plantillas de redacción (get_plantillas_retriever)

  4. python main.py --no-judge
     → Pipeline sin evaluación automática (para pruebas rápidas)

  5. python main.py --question "¿Cuántas portaciones hubo en Q4 2024?"
     → Pipeline con pregunta personalizada

Pipeline completo (cmd_run_pipeline):
  1. Loguea configuración (modelo, URL Ollama, BD PostgreSQL)
  2. Verifica conexión a PostgreSQL con test_connection()
  3. Crea Orquestador e invoca run(question)
  4. Si no --no-judge: crea LLMJudge e invoca evaluate(ctx)
  5. Almacena resultado del juez en ctx.judge_result
  6. Invoca build_word_document(ctx, judge_result)
  7. Muestra ruta del .docx generado y estado final
  8. Guarda el login output/run.log

Pregunta por defecto (DEFAULT_QUESTION):

6. DECISIONES DE DISEÑO NOTABLES
================================================================================

6.1 Todo local, sin dependencias de APIs externas
  El sistema usa Ollama con llama3.1 y nomic-embed-text, ambos corriendo
  localmente. No requiere claves de API de ningún servicio externo.
  Esto es relevante para un contexto regulatorio gubernamental donde
  la confidencialidad de los datos de portabilidad es crítica.

6.2 Resiliencia del pipeline
  El método _safe_run() en BaseAgent garantiza que el fallo de un agente
  individual NUNCA detenga el pipeline completo. El AgentResult captura
  el error y el pipeline continúa. El documento Word reflejará los errores
  con texto en gris.

6.3 Portabilidad cross-platform (Mac/Windows)
  - Todas las rutas usan pathlib.Path (nunca strings con barras hardcodeadas)
  - str() explícito para ChromaDB que no acepta Path en todas las versiones
  - use_multithreading=False en DirectoryLoader por estabilidad en Windows
  - encoding="utf-8" con awareness de que Windows puede requerir "utf-8-sig"

6.4 Separación de responsabilidades
  - config.py: toda la configuración
  - Orquestador: solo coordinación (no evalúa ni genera Word)
  - main.py: CLI + orquestación de alto nivel (juez + Word)
  - Cada RAG: su propia colección y directorio, sin colisiones
  - BaseAgent: interfaz + manejo de errores, sin lógica de negocio

6.5 Temperaturas diferenciadas por agente
  - AgenteDatos:       0.0 → SQL debe ser determinista y exacto
  - AgenteRegulatorio: 0.1 → Preciso con mínima variación para citas legales
  - AgenteRedactor:    0.3 → Prosa más fluida y menos repetitiva
  - LLMJudge:          0.0 → Scoring determinista y reproducible

6.6 Coloreado por agente en el documento Word
  Cada agente tiene un color RGB asignado en el Word final para trazabilidad
  visual:
    Azul   → Agente Datos (cifras y análisis cuantitativo)
    Verde  → Agente Regulatorio (citas normativas y marco legal)
    Rojo   → Agente Redactor (informe narrativo integrado)
    Morado → LLM Judge (evaluación automática)
    Gris   → Metadatos y errores

6.7 Idempotencia de los vectorstores
  Los vectorstores no se re-ingestan si ya contienen datos, a menos que
  se use force_reingest=True o el flag --reingest. Esto acelera las
  ejecuciones sucesivas.

6.8 SQL Agent con patrón ReAct
  Se usa "zero-shot-react-description" en lugar de "openai-tools" porque
  modelos locales como llama3.1 no soportan tool-calling estructurado
  de forma nativa. El patrón ReAct es más robusto para estos modelos.

6.9 Parsing robusto del JSON del juez
  Los LLMs locales frecuentemente agregan texto antes/después del JSON.
  El juez usa re.search(r'\{.*\}', raw, re.DOTALL) para extraer solo
  el bloque JSON. Si falla, retorna un resultado de fallback seguro
  (nunca crashea).

6.10 Contexto acumulativo entre agentes
  Cada agente recibe no solo la pregunta original, sino también los outputs
  de TODOS los agentes anteriores:
    - AgenteRegulatorio recibe datos_result para contextualizar legalmente
    - AgenteRedactor recibe datos_result + regulatorio_result para integrar

9. FLUJO DE EJECUCIÓN COMPLETO (PASO A PASO)
================================================================================

  1. El usuario ejecuta: python main.py
  2. setup_logging() configura logging dual (consola + archivo)
  3. parse_args() procesa argumentos CLI
  4. Se importa config.py y se cargan variables de .env
  5. Se verifica conexión a PostgreSQL con test_connection()
  6. Se instancia Orquestador() → instancia los 3 agentes
     (cada agente crea su ChatOllama y su retriever RAG)
  7. Pipeline secuencial:
     a. AgenteDatos._safe_run(question)
        → RAG schema → SQL Agent → queries contra PostgreSQL → cifras
     b. AgenteRegulatorio._safe_run(question, datos_result.content)
        → RAG regulatorio → cadena LCEL → análisis normativo
     c. AgenteRedactor._safe_run(question, datos_result.content,
                                  regulatorio_result.content)
        → RAG plantillas → cadena LCEL → informe narrativo integrado
  8. Se crea LLMJudge y evalúa el RunContext:
     → Califica en 5 dimensiones → JSON → JudgeResult
  9. build_word_document(ctx, judge_result)
     → Genera .docx con secciones coloreadas por agente
  10. Se muestra la ruta del documento y el score del juez
  11. Log completo disponible en output/run.log

Tiempo estimado de ejecución: Variable, dependiendo del modelo LLM y
la complejidad de las queries SQL. El timeout del SQL Agent es de 3 minutos.
Ejecución típica completa: 3-10 minutos.
